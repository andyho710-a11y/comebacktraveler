## 歡迎訊息草稿

## 最低成本通知現況與選項

已完成：先交易儲存詢單，管理頁重新讀取；前景頁面每 30 秒輪詢並只顯示泛化提醒。零第三方 API，但手機背景或休眠時無可靠通知，**不能替代在家待單的正式通知方案**。

待核准選項：

- 若未來有常駐 HTTPS 主機，可用 Web Push＋Service Worker，但仍需建立推播訂閱、VAPID 私鑰、安全送達／重試紀錄及手機相容驗收，不是只開瀏覽器權限就完成。
- 若申請 LINE OA，官方歡迎訊息與關鍵字回覆可先由 OA Manager 設定；通知經營者可用 Messaging API push，但需核實帳號方案、接收人 user ID、好友關係、配額及最新費率後再批准，不能承諾免費。個人帳號沒有此功能，也不採已停止的 LINE Notify。
- 若有已核准的寄信服務，可傳「有新的行程詢問，請登入管理後台」與固定後台入口；不寄姓名、電話、路線、精確日期或含 bearer token 的連結。此次不讀取或重用 `/services` 的 SMTP 密碼。

## Messaging API 擴充契約（尚未接線）

經核准 OA 與成本後，獨立同源 backend webhook 先以 raw body 和 Channel Secret 驗證 `x-line-signature` HMAC-SHA256，使用 timing-safe compare；驗證前不得解析／記錄客戶內容。驗證後限制 body、處理 event ID 去重，儲存加密草稿與事件 receipt，回覆通用「已收到詢問，將人工聯繫」。以 outbox 在資料寫入成功後通知管理員，保留 retry／dead-letter，避免外部發送失敗把已儲存詢單當作失敗重建。

Channel Secret／Token 只進受保護 runtime secret store，不放 `PUBLIC_` 變數、前端或 Git。來源 `line` 為 enum；LINE user ID 與對話識別碼視為個資，加密、最小化、訂保留期，不送 GA4。客服文字入後台只能是待確認詢單，不能自動設 booked。所有 reply／push 的報價與正式預約語句須經人工及車隊程序，不自動收款。

## Phase 4 AI（設計，未啟用）

先用既有結構化表單減少工作，不急著加 AI。之後可在本機／已核准模型將去識別需求整理成日期、區域、往返、等待、停靠、人數與容量提醒；缺欄位列待詢問，不補造。聯絡方式從提示移除，客戶病況等敏感資訊不外送。模型輸出一律當草稿，驗證 schema、保留人工審核，禁止存取付款、派遣、狀態確認與訊息發送工具。先以假資料驗收，再評估成本與資料處理條款。
